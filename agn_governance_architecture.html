Rogue User & Agent Threat Detection and Response

End-to-end architecture separating asynchronous security intelligence from synchronous preventive enforcement. Proposed design; not a statement of deployed PNC systems.

2. Real-time preventive enforcement · independent of the detection pipeline

User / Agent RequestIdentity, workflow, intended action
AGN Framework / Gateway PEPIntercept tool, API and data access
Policy Decision PointRBAC, agent grants, allowlists, kill state
Allow or Deny?Fail safely for protected actions
Allow → execute
Deny → block + eventTelemetry feeds pipeline above
Important: a denied action is blocked before execution. Kafka, incident processing, and ML scoring are not prerequisites for this decision. Network and data-service enforcement must prevent gateway bypass.

5. Response ladder

  1. LOW Log and monitor.
  2. MEDIUM Alert security analyst; create or update incident.
  3. HIGH Block prohibited action; investigate and consider run quarantine.
  4. CRITICAL Preapproved containment: cancel run, revoke capabilities, disable workflow if justified.
  5. RECOVERY Verify containment, require authorized restoration, preserve audit evidence.

6. Suggested implementation order

  1. P0: Map sources, identities, and unified events.
  2. P0: Add AGN/gateway policy enforcement and deterministic denies.
  3. P0: Implement incident records, audit, manual kill switch and cancellation.
  4. P1: Add baselines, risk scoring, event correlation, and analyst dashboard.
  5. P1: Add controlled automated containment.
  6. P2: Calibrated ML threat models and multi-agent graph detection.
Design considerations: enforce least privilege, minimize sensitive telemetry, keep immutable audit evidence, use explicit approval boundaries, and verify cancellation and network egress coverage. OCSF may require extensions for agent-specific events.
